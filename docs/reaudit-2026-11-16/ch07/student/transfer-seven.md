# Перенос: ремонтная служба, ровно 7 проверок

Решение принимается до повторной поломки; признаки доступны после первичного ремонта. На одной и той же исторической дате обе модели сортируют одни и те же устройства. Вероятность — по убыванию; при точном равенстве выбираю меньший device_id. Правило фиксирую до открытия исходов. Беру первые семь строк, а не всех с p ≥ седьмой оценки.

Придуманный мной численный пример (не результаты производственных данных):

| ID | A | B | Позже повторная поломка |
|---|---:|---:|---:|
| D01 | .95 | .10 | 1 |
| D02 | .90 | .40 | 0 |
| D03 | .80 | .40 | 1 |
| D04 | .70 | .40 | 0 |
| D05 | .60 | .50 | 1 |
| D06 | .50 | .60 | 0 |
| D07 | .40 | .70 | 1 |
| D08 | .40 | .80 | 0 |
| D09 | .40 | .90 | 0 |
| D10 | .20 | 1.00 | 1 |

Очередь A: D01, D02, D03, D04, D05, D06, **D07**. D08 и D09 имеют тот же риск .40, но остаются вне бюджета. Порог p≥.40 дал бы девять проверок.

Очередь B: D10, D09, D08, D07, D06, D05, **D02**. D03 и D04 тоже имеют .40, но правило ничьих оставляет их за границей. Обе очереди ровно по 7 мест. A находит 4/5 повторов (precision 4/7), B — 3/5 (precision 3/7). Последний допустимый ID указан явно, индексы нельзя сбрасывать независимо от вероятностей. Большие численные вероятности B не делают её победителем. Подбор и повторные проверки — на train/validation; один фиксированный финал не используют для следующих настроек.
