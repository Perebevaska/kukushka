# Самостоятельное прохождение главы 15: исходный замороженный результат

Профиль: аналитик SQL/Excel после собственных глав 1–14. Метод — публичный Cognitive Walkthrough: до действия записаны цель Q1, доступное действие Q2 и конкретный ожидаемый результат Q3; после — сырой ответ Q4 и следующий шаг в `walkthrough.jsonl`. Прочитан полный маршрут: intro → 01 → 02 → 02b → 03 → 04 → 05 → 06 → открытый ответ → тест. Все 19 теоретических PNG и два фактических графика browser просмотрены, три собственных графика EDA тоже. `reading-order.jsonl` содержит технический повтор записи step1 из повторно использованной шапки: это не дополнительное чтение в другом порядке. ## Наблюдения со стабильными ID

**ST-01 — имена входов скрыты за краткой заготовкой.** В `01/contract` условие называло p_ok/p_bad1/p_bad2, но не имена исходных трёх таблиц. Я предположил ok/bad1/bad2, и это прошло. В `02/reasons` предположил CARD по теории, получил NameError; заменил его на `model.feature_names_in_`, прошло. В `03/lucky` предположил g, получил NameError; добавил явный read_csv, прошло. Наблюдение: видимая заготовка не всегда полностью показывает доступные имена. Гипотеза человеческого темпа: поиск скрытой переменной отвлечёт от нового понятия. Улучшение: показывать короткий перечень гарантированно доступных объектов и тип/форму каждого.

**ST-02 — собственная ошибка генерации кода.** В первом `02/http` мой строковый генератор превратил `sep='\n'` в разрыв литерала. Реальный SyntaxError указал строку; заменил на `sep=chr(10)`, принято. Это не дефект учебной формулы и не основание упрощать тему JSON. Сохранил ошибку вместо маскировки успешным повтором.

**ST-03 — первый handler завершился средовой ошибкой.** `02/handler` сначала получил ModuleNotFoundError sklearn до содержательного результата; повтор того же обработчика с исправленным print прошёл. Не утверждаю причину внутри среды, поскольку setup не читал. Это отдельное наблюдение о надёжности запуска, не свидетельство неправильного понимания handler.

**ST-04 — видимый текст отстал от актуального исполнения.** В 06 prose пример kNN указан 0,714 (и 0,733 при перемешивании), тогда как самостоятельный и browser grouped запуск одинаково дали 0,724. Это не моя неудачная сдача: models принята. В quiz 06/2 «42 из150» сопровождается «остальные84», хотя осталось108. По смыслу выбрал положительную пользу, вопрос принят. Нужна единая генерация контрольных чисел или явная пометка условий старого расчёта.

**ST-05 — экономическая проверка выявила больше, чем AUC.** На ранних OOF срезах положительное ожидание очередей 134344 / 318364 / 253199 ₽, но сценарий на наблюдаемых уходах −43033 / +25119 / −11919 ₽. Это реальные собственные расчёты до открытия июня; записаны в decision-note-before-test.md. Вероятности верхнего квинтиля в среднем близки (0,292 против0,272), однако это не проверяет калибровку в дорогом денежном хвосте. Гипотеза обучения: студент может назвать модель выгодной по формуле, не проверив такой разрыв. Улучшение: обязательное сравнение ожидания и сценария по очереди в каждом прошлом квартале, до позднего теста.

**ST-06 — перенос действительно проверяет самостоятельность.** Собственный score.py из README с `--call-limit 3` без редактирования ячеек дал C0115/C1263/C1247, все Уфа, ожидание124874 ₽. Метаданные сохраняют полный итог, лимит, экономику, хеш и версию. Мой selfcheck загрузил модель, сверил20 golden, оба списка, города и паспорт; независимый получатель ещё должен повторить это сам. Практическую мини-приёмку стоит вводить до выпускного, начиная с артефакта главы7/8.

**ST-07 — маршрут различает чтение и исполнение.** FastAPI и MLflow нативно запущены, Docker только прочитан. Browser batch/latency не является веб-сервером, Parsons log_model не является реестром, прочитанный Dockerfile не является собранным образом. Я веду эти статусы отдельно. Хорошо, что intro прямо предупреждает о недоступности части инструментов в браузере; полезно добавить видимый журнал «прочитал / выполнил / проверил перенос».
