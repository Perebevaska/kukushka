## Реально выполненные изменения

**PS15-01 — граница возвратов.** В общей функции признаков добавлена `revenue_trend`: при точно нулевом знаменателе возвращает0 по публичному соглашению. Проверки: (100,50)→0,3311258; (−5,3)→8; (−1,0)→0. Значения вне[−1,1] не обрезаются. Отдельная интеграционная копия данных содержит единственный возврат−1 у действующего офиса: строка проходит через настоящий `build_features`, затем подготовку сохранённой модели без NaN/inf. Числовые входы всех пяти срезов конечны. Исходная CRM даёт прежние65 строк,443403руб,20golden maxdiff9,45e−17. Бинарная модель и первая фиксация выбора не менялись.

**PS15-02 — одиночные признаки и первичные даты.** Использованы только три ранних среза и те же пять групповых фолдов. Для каждого одиночного признака обучается логистическая модель внутри фолда; категориальные значения one-hot без произвольного порядка, числовые — imputer/scaler. Сохраняются ROC-AUC/AP по фолдам, средние, сырое направление и знаки коэффициентов. Сильнейший `orders_90`:AUC0,697243, отрицательный знак во всех5 фолдах; `revenue_90`0,682893; `tickets_90`0,671980 с положительным знаком во всех5. Это диагностические сравнения на разработке, не новый выбор по июню.

Для сильнейшего сигнала сохранены первичные заказы с ID, датой события, регистрации, начала договора и срезом. На трёх ранних срезах6689/9481/10741 использованных заказов; ни одного после среза, до регистрации или до договора. Время загрузки в систему не наблюдается, поэтому доступность подтверждена по дате события, а не по журналу поступления. Отдельные изменения одного будущего заказа, одного будущего обращения и оплаты после среза не изменили ни одной строки прошлых признаков при сверке по ID.

Дубли обращений:142 дополнительных строки по142ID, конфликтов содержательных полей нет. После дедупликации флаг A выявляет89 обращений у82 офисов до регистрации; B — ещё35 у34 между регистрацией и договором. Вместе124 у109 разных офисов. Сохранены конкретные ID и все три даты. Исключение A меняет число обращений у7/8/10/12/7 офисов по пяти срезам; A+B — у10/11/12/17/8. Полные выровненные таблицы и список изменившихся офисов доступны в `reports/revision/ticket-count*.csv`. Это именно изменение признаков, не утверждение, что все124 события влияют на каждый срез. Альтернативные counts не использованы для нового обучения: изменение AUC и рублей не измерено. Источник B и реальное время появления обращения неизвестны.

**PS15-03 — отраслевой анализ воспроизводится.** Теперь `python revision.py` и отдельная ячейка полного блока пересоздают `industry-ablation.json` на тех же ранних фолдах: без отрасли0,7943197 против0,7920802 с ней. Перед чистым запуском файл удалён только в новой рабочей копии, после RunAll он снова появился. Исходный выбор LogReg оставлен; это дополнительный объяснительный результат после заморозки.

Новый публичный бриф поясняет ограничение симулятора: прошлые заказы зависят от последнего состояния health и заранее выбранного ухода. Это допускает выполнение механики временного отбора, но не устанавливает реальное последовательное происхождение истории. Направление и размер переноса качества на реальные будущие кварталы неизвестны. Удержание0,5 — сценарий, а не измеренный эффект. Флаги A/B дат не являются экспериментальными группами.
