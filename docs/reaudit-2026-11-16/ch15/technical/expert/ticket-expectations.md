Уточнение перед контрастной проверкой по ID, после первичного счёта в profile.log. До наблюдения данных ожидается, что событие поддержки существующего офисного клиента имеет устойчивый ID, единственную дату и допустимую связь с датой входа клиента в систему; историческая выгрузка не даёт права задним числом предполагать, что обращение импортировано из другой системы. Не предполагаем заранее, что событие между регистрацией и договором обязательно невозможно. Для сопоставления определяем A = created_at обращения < created_at клиента, B = created_at клиента ≤ created_at обращения < start_date. Категории не пересекаются. Предварительное ожидание для контрастных сценариев: исключение A затронет только офисы с A в окне, исключение всех A∪B затронет не меньше офисов. Все остальные поля и ID должны сохраняться; метрики и оба состава очередей требуется пересчитать только при принятии новой политики в учебный канон. На этой стадии фиксируем диагностический результат на замороженной БД, без замены данных, оценок модели и судейских списков.
