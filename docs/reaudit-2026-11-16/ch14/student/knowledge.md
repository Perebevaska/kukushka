## Прочитал и могу объяснить до отправок

Изображение — массив: серое (h,w), цвет (h,w,3), набор (n,h,w), PyTorch (n,c,h,w). Строка идёт вниз. uint8 экономит память, но арифметика может переполниться, поэтому float/int нужен до вычитания или сложения. PNG хранит маску точно, JPEG изменяет значения; память не равна размеру файла.

Фильтр считает сумму произведений в окне; в уроке это correlation без переворота. nearest продолжает край, constant добавляет искусственный перепад. Размытие до Собеля гасит шум. Пулинг снижает размер и частично чувствительность к положению; переход через границу блока может изменить результат. Global теряет детали.

CNN учит локальные общие веса; у ReLU и пулинга весов нет. Число параметров conv = (k*k*c_in+1)*c_out. Размер карты и receptive field различаются: карта уменьшается, поле растёт. Случайные фильтры остаются фиксированными, учится классификатор сверху. Transfer использует настоящие предобученные веса; кривая случайных фильтров не становится измерением ResNet.

Заморозка requires_grad отключает обновление параметров, но буферы BatchNorm в train могут меняться; фиксированное тело держат в eval. Обычная test accuracy не проверяет новый свет. Аугментация применяется после split; стресс на тех же ID создаёт парное сравнение, а не новый независимый набор.

IoU = inter / (areaA + areaB - inter). Пересечение без max(0, ...) может стать положительным из двух отрицательных сторон. Для масок считаются & и |. Детектор проверяется по убыванию confidence, одна true рамка засчитывается один раз. NMS отдельно подавляет перекрывающиеся дубли.

Из покадровых pred==0 строятся события по ключу (day, time, slot); два соседних номера строк не заменяют интервал 15 минут. Пропуск кадра ломает подтверждение. Цену правила определяют ложные, пропуски, повторы и задержка, а не только accuracy. 0.25 часа пустого наблюдения дают ячейко-часы, а не время закрытия магазина и не измеренную экономию от переноса партии.

## Реально выполнено после CPU FREE

Все 94 цели закрыты; исходные input и output сохранены. Сам создал X2d после NameError в knn-k, разобрал контракт episode_metrics после одной подсказки и передал широкую bool-таблицу. До этого ошибку не умел локализовать по сообщению TypeError внутри готового помощника. Parsons нужно собирать из предоставленных строк: эквивалентный произвольный код через helper не заменяет доступный элемент.

Проверил арифметику памяти, roundtrip PNG/JPEG, uint8 saturation и срезы, ручные фильтры, pooling, модели sklearn, stress с фоном, random features, загрузку папок, IoU/matching/NMS. Реальные численные выводы находятся в feedback, дневнике и walkthrough. Не считаю чтение prose дополнительным inference.

Настоящий PyTorch CNN исполнен отдельно: 25 эпох, 23556 параметров, последняя test accuracy .982; циклический сдвиг .974, тусклый свет .868. Этот опыт проверяет roll, а не уход части кадра за край. Промежуточный test печатался каждую эпоху по опубликованному примеру; я не выбирал checkpoint по лучшей эпохе и не называю этот тест валидацией для настройки архитектуры. В native запуске thread1, stderr пуст.

Настоящие cached ImageNet ResNet-18 признаки вычислены после фиксации проекта и открытия второго дня. При 200 фото на класс random/ResNet на обычном контроле .940/.982, на следующем вечере .804/.765. При 50/100/200 ResNet на следующем вечере .691/.725/.765: больше фото в этом опыте помогло относительно 50, но не даёт линейного обещания ещё 1000. Random features при 200 оказались лучше в другом свете. Условия и ID общие; это два синтетических источника, не гарантия для реальной камеры. Нового обучения ResNet тела или fine-tuning в этом опыте не было: это замороженный извлекатель с LR сверху. Расчёт trainable/head в браузере сам по себе не является исполнением fine-tuning.

Свой проект создал отдельно из видимых NPZ и теории, проверил перестановку строк, сохранил k2 и цены до day2. Получил эпизоды, ложные/пропуски/повторы и задержки. В наблюдении и симуляции различаю ячейко-часы, минуты задержки и рубли заданной функции потерь; настоящее экономическое решение требует новых наблюдений и цен.

Дополнительная собственная проверка переноса на парковку исполнена в event-checks.py. Полный журнал2,0,0 даёт сигнал12:30, удаление12:15 убирает сигнал, перестановка строк не меняет результат. В моём первом открытом ответе45минут от09:30 до10:15 были разницей времени от первого наблюдения свободного места; из-за пропуска09:45 это не доказанная задержка внутри одного непрерывного истинного эпизода. Код с разрывом неизвестного интервала выделяет два наблюдаемых эпизода: первый пропущен, второй обнаружен через15минут, cost315 при моих условных ценах. Первый ответ сохранён, это уточнение после собственного исполнения. Для реального паркинга нужен явный способ обращения с неизвестным состоянием между снимками; нельзя молча подменить его непрерывностью.
