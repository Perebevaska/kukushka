## C01. Корректная распаковка приводит к ложному обвинению в ручной сумме

[Условие и проверка](../../../content/ch01/exam-1.md#L402). Обещание: разобрать непустые строки функцией и посчитать сумму произведений. Требования оставлять объявление `text` отдельной строкой нет.

Минимальная корректная программа `C-P05`:

```python
def parse_line(line):
    city, cups, price = line.split(';')
    return [city, int(cups), int(price)]

text, total = 'Пермь;412;205\nКазань;538;198\n\nТюмень;297;214\n', 0
for line in text.splitlines():
    if line:
        _, cups, price = parse_line(line)
        total += cups * price
```

Ожидался зачёт. Оба рантайма: `ok=true`, `passed=false`, дословное сообщение: «На новой выгрузке total неверен: обработайте все непустые строки, не вписывайте сумму.» На исходном тексте решение считает 254542. Если заменить сам вход на контрольный `Уфа;7;113\n\nОмск;11;127\nСамара;3;149\n`, тот же цикл считает 2635.

Причина на строке 435 исходника: `visit_Assign` ищет только непосредственную цель `ast.Name('text')`. При распаковке непосредственная цель — `ast.Tuple`, поэтому подмены нет. Повторный запуск снова получает сентябрьский текст вместо нового. Общий `rerun_with` в [harness.py](../../../site/assets/harness.py#L263) уже умеет обходить вложенные цели; локальная реализация `parse` отличается от него.

Минимальная правка: обходить имена с контекстом `Store` внутри каждой цели, сохранив запрет замены при чтении `text` справа:

```python
any(isinstance(n, _ast.Name) and n.id == 'text'
    and isinstance(n.ctx, _ast.Store)
    for target in node.targets for n in _ast.walk(target))
```

Критерий приёмки: принять `C-P01`, `C-P02`, `C-P05`; продолжать отклонять `C-P04` с обходом обязательной функции и программу с готовым `total`. Проверить также нормализацию `text = text.strip()`, чтобы исправление не перезаписывало вычисленное значение. Этот предложенный патч в курс не вносился и отдельным изменённым чекером здесь не прогонялся.

## C02. Сравнение равенства пропускает неправильные типы

[Явное требование типов](../../../content/ch01/exam-1.md#L404): «числа — `int`». Программа `C-P03` отличается от принятой `C-P01` только строкой возврата:

```python
return [city, float(cups), float(price)]
```

Ожидался отказ. Оба рантайма: `ok=true`, `passed=true`, `msg=""`. Функция возвращает `['Уфа', 10.0, 200.0]`; число в `total` также становится дробным. Причина: `10.0 == 10`, а проверки сравнивают только значения списка и суммы.

Последствие: карточка подтверждает освоение преобразования в `int`, хотя ученик применил другое преобразование. Это не расхождение арифметической суммы на данном наборе, а нарушение явно указанного контракта результата.

Минимальная правка: получить результат одного вызова в переменную, проверить список нужной длины, значения и `type(row[1]) is int`, `type(row[2]) is int`. Желательно делать это и в обёртке `_record` для всех переданных непустых строк. Сообщение: «Чашки и цена должны быть целыми числами int; сейчас получены float.» Критерий: принять `C-P01/02/05`, отклонить `C-P03` именно с объяснением типа.

## C03. Политика сохранения первого дубля не проверяется на различающихся строках

[Шаг 2](../../../content/ch01/14-project.md#L151) прямо требует первое вхождение; [шаг 8](../../../content/ch01/14-project.md#L577) предлагает перенести этот код и обещает работу на другой месячной выгрузке.

Независимая программа с `Counter`, чтением CSV, журналом и `Path.write_text` принята (`C-F01`). При замене только дедупликации на обычное обновление словаря:

```python
by_id = {}
for o in orders:
    by_id[o['order_id']] = o  # перезаписывает первым встреченную запись
clean = list(by_id.values())
```

`C-F02` также получает `ok=true`, `passed=true`, `msg=""` в обеих средах. На предъявленных данных дубли одинаковы; встроенная октябрьская выгрузка тоже повторяет те же суммы.

Различающий вход сохранён целиком в `files_override` программ `C-F04/05`: это октябрьский CSV из семи записей, в котором у `O3` первая сумма 230, повторная — 1230. Остальные строки соответствуют встроенному октябрьскому примеру. При одном битом значении и двух лишних дублях нужно принять четыре заказа на 1265 ₽. Последнее вхождение даёт 2265 ₽ при том же балансе строк `7 = 4 + 1 + 2`.

На таком CSV текущий чекер правильно принимает первое вхождение (`C-F04`) и отклоняет последнее (`C-F05`): «Проверьте поле «Учтённая выручка»: в отчёте «2265 ₽». Сверьте значение с принятыми заказами и журналом.» Значит, ошибка находится в различающей способности штатного набора, а не в сравнении готового отчёта. Полные фактически записанные `report.md` сохранены в `report_md` результатов.

Минимальная правка: у одного повторного ID во встроенной октябрьской выгрузке изменить сумму, оставив первой исходную запись; при необходимости добавить обычный день/напиток для проверки сохранения остальных полей. Критерий: первая версия принята, last-wins отклонена; полный журнал по-прежнему сходится.

## C04. Дополнительная карточка: isdigit и int совпадают только на текущем списке

[Условие](../../../content/ch01/12-errors.md#L364) определяет плохую строку через отказ `int()` без чистки. Правильная версия `C-N01` использует `try/except ValueError`; другая `C-N02` делает:

```python
for value in raw:
    if value.isdigit():
        total += int(value)
    else:
        bad += 1
```

Обе приняты с пустым сообщением. Для данного конкретного списка это численно правильный ответ. Считать сам зачёт ошибкой фиксированного задания было бы чрезмерно: условие не требует функцию или явный тест на другом списке. Однако проверка не устанавливает перенос именно указанного правила «берёт int как есть».

Адресный перенос — `[' -50 ', '+20', '30', '60']`. `int` принимает все четыре строки без предварительной чистки. Правильная сумма 60, ошибок 0 (`C-N03`). Принятая ветка с `isdigit()` получает 90 и 2. В `C-N04` сохранена отдельная проверка переноса, а не подмена штатного вердикта: «total = 90; int accepts all four strings, sum should be 60». Этот случай исполнен в обеих средах.

Предложение: добавить один повтор через `rerun_with(raw=[' -50 ', '+20', '30', '60'])` и конкретное сообщение о знаке/пробелах по краям. Критерий: `try/int` принимается на обоих списках, фильтр `isdigit` отклоняется на переносе. Это P3 усиление проверки понимания, а не доказанный P1/P2 дефект карточки.
