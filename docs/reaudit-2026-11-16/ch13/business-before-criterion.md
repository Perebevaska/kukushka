# Глава 13. Критерий делового вывода до сверки с другими ролями

Версия 563d774. Основание — вопрос управляющей во введении, проект «Отзывы о кофейнях» и заголовки CSV. Зафиксировано до чтения отчётов и до подсчёта результатов. Управляющая решает, какой точке поручить сверку заказов в начале ноября 2026 года. Бюджет на чтение всех сообщений и на изменение процесса не задан. Выбираю одну точку для проверки.

1. Наблюдение — один уникальный review_id опубликованного отзыва с онлайн-карт в сентябре и октябре. Разные ID с одним текстом остаются разными наблюдениями. Уникальных авторов, всех посетителей, числа покупок и доли обоснованных претензий выгрузка не содержит. Сигнал модели учится предсказывать рейтинг ≤ 3. Это отдельное измерение от упоминания проблемы в тексте, темы, чувства автора и подтверждённого нарушения по заказу.
2. До открытия результатов фиксирую правило разведочного выбора. В каждом магазине сначала сравню календарные [1 сентября, 1 октября) и [1 октября, 1 ноября), минимум 30 отзывов с каждой стороны. Возьму максимальную разность долей (при равенстве — по shop_id). Внутри выбранной точки отдельно возьму максимальный положительный рост между соседними полными неделями понедельник–воскресенье при n ≥ 30 в каждой. При равенстве возьму раннюю дату. Затем пересчитаю ВСЕ отзывы точки в [1 сентября, начало выбранной недели) и [начало выбранной недели, 1 ноября). Укажу, что выбор максимума на этих данных даёт повод проверить точку, а точную дату начала изменения он не устанавливает. Проверю соседние недели. Для воспроизводимой независимой сверки без обучения заранее выбираю буквальный индикатор «не советую» в исходном тексте без учёта регистра. Покажу отдельно его охват, ход сигнала штатной модели, где результат доступен, и верификацию синтетической меткой. Границу не буду сдвигать для совпадения с ключом проекта.
3. Соединение по полному множеству ожидаемых ID, взаимная уникальность, совпадение даты и точки с сырьём. Отдельно сообщить n всех подходящих, n с ответом, n с меткой, n пропусков и конфликтов, число сигналов и жалоб. При дублирующемся ID, неизвестном ID или перемешанном безымянном выводе нельзя выдавать долю по «совпавшим» позициям. Строку с ошибкой разбора сохранить с причиной и исключить из знаменателя распознанных с явной оценкой покрытия. При u неизвестных и k найденных жалобах диапазон по всем N равен [k/N,(k+u)/N]. Для темы знаменатель — все сигналы точки данного периода (либо все жалобы по названному источнику) с указанием неизвестных тем.
4. Воспроизводимое правило для людей: «жалоба» — конкретная описанная нежелательная ситуация, в том числе в смешанном отзыве. Негативный тон без ситуации, отсутствие жалобы и неоднозначная ситуация различаются; сомнения отмечаются. Тема относится именно к проблеме. «Обоснована» дополнительно требует единого критерия подтверждения, например сопоставимого заказа с обещанным и фактическим временем. Невозможность связать заказ оставляет статус неизвестным. Для реальных выводов нужны независимые от сигналов выборки из обоих периодов, включая сигналы и пропуски модели, одинаковые правила, слепая разметка, разбор расхождений, оценка неопределённости разности. В случае неодинаковых вероятностей отбора нужны веса. Звёзды, метки генератора, LLM и мои иллюстративные чтения не заменяют эту работу.
5. Короткая цитата воспроизводится по ID, её содержание должно поддерживать названную проблему; несколько цитат проверяют смысл, частоту задают счётчики. Для суждения о причине понадобится сопоставимая операционная метрика (например, опоздали / все доставки), календарь/канал, состав заказов и сверка в других точках. Для изменения процесса понадобятся проверка предполагаемого механизма и сравнение исхода с сохранением процесса на сопоставимых заказах. Одна проверка журнала может быть оправдана даже при отсутствии оснований менять смену или подрядчика.
6. Отдельно дать открытую карточку службы поддержки до решения и письма. При смене классификатора нужно различить изменение объёма, состава обращений и способа измерения. Ретроспективный перекрёстный прогон обеих версий на одних ID и независимые человеческие метки в обоих периодах отвечают на разные вопросы. Совпадение поправки с долей на записях, по которым оценены TPR/FPR, не проверяет перенос на новую неделю.
