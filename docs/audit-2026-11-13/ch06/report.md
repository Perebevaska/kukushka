## От прогноза к списку для акции

В исходной таблице 2 400 разных карт и 535 случаев ухода. Поле `card_blocked` особенно заманчиво: из 530 заблокированных карт 507 относятся к ушедшим. У незаблокированных это 28 из 1 870. В [генераторе](../../../tools/gen_data.py) порядок явный: сначала определяется `churned`, затем по нему генерируется блокировка. Хорошая точность правила не делает этот признак доступным на день отбора. Дата среза требует исправления: в [условии](../../../content/ch06/09-project.md) указан октябрь, в комментарии генератора — декабрь, а в [CSV](../../../site/data/guests_churn.csv) отдельной даты нет. Эти данные иллюстрируют прогноз, но не позволяют эмпирически проверить перенос на следующий период.

Попросите ученика заранее зафиксировать дату решения, признаки, бюджет контактов и метрику для списка из 10% карт. Затем разделите два результата: ретроспективный список для проверки по уже известным ответам и список на сегодняшний день для контакта с гостями, чьи ответы пока неизвестны. Если в демонстрации утечки уже показан результат на 600 картах, сохраните отдельную выборку для первого честного показа финального результата. Приёмка: на таблицах за два разных месяца ученик создаёт список для второй даты, не используя её будущие метки; отдельно показывает, сколько уходящих попадало в 10% на учебном периоде. В курсе стоит сохранить прямую оговорку о том, что польза самого бонуса проверяется экспериментом.

Для бизнес-сравнения держите одинаковым число контактов. На тестовой части 600 гостей, 134 впоследствии ушли. Accuracy константы («никто не уйдёт») — 77,67%, правила 45 дней — 85,17%, леса — 89,83%. В 60 контактах лес обнаружил 57 ушедших, сортировка по давности визита — 53. У 40 из модельных 60 к тому моменту последний визит уже был более 45 дней назад. Если задача маркетинга — найти ещё активных, в этой подгруппе бюджет 53 контакта: модель нашла 40 будущих уходов, давность — 19. Эти числа описывают один отложенный набор, а не эффект начисления бонусов. [Независимое сравнение и границы](methodist.md).

**Проверять саму сданную модель.** В `09-project/final` можно оставить ранее вычисленные правильные числа, переобучить объект `model` на нулевых метках и всё равно сдать шаг. Следующий шаг самостоятельно создаст другой лес. Проверка должна сравнить прогнозы **объекта ученика** с заявленными числами. Приёмка: исходная и другая корректная реализация приняты, модель, которая всегда предсказывает отсутствие ухода, отклонена при заявленной accuracy 89,83%. В упражнении о калибровке отдельно предъявить вероятности 0, 0,25, 0,5, 0,75 и 1 и потребовать, чтобы число объектов по интервалам совпадало с числом прогнозов.
