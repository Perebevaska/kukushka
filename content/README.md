# Как писать уроки

## Для кого курс

Аналитики, которые знают SQL и Excel, но в Python и DS — новички или с разрозненными знаниями. Значит:

- объясняем просто, без жаргона; новый термин — сразу с расшифровкой;
- опираемся на то, что читатель уже знает: SQL, Excel, отчёты. Аналогия с SQL — в блоке `::: sql`;
- одна идея за раз: короткий абзац → живой пример → следующий шаг;
- ничего не используем в задачах до того, как это объяснено. Исключение — задачи «со звёздочкой», там можно попросить догадаться, но с подсказками;
- сквозная история — сеть кофеен «Зерно». Данные, примеры и задачи — свои, придуманные или из открытых источников с совместимой лицензией.

Скелет программы (порядок тем и шаг сложности) сверяется с общепринятой программой DS. Тексты, примеры, задачи и датасеты сторонних курсов **не используются и не пересказываются**.

## Файл урока

`content/<глава>/<урок>.md`, урок перечислен в `course.yaml` со статусом `ready` или `draft`.

```markdown
---
title: Переменные и числа
lead: Одна-две фразы — что будет в уроке и зачем.
files: [orders.csv]          # необязательно: файлы из site/data/ для всех запусков урока
recap:                       # «Что запомнить» в конце урока
  - "`round(x, 2)` округляет до двух знаков."
---

## Раздел теории

Текст. Блок ```python — живой пример: его можно менять и запускать.
Варианты: ```python error — пример, который специально падает с ошибкой;
```python static — просто код без запуска; ```text — образец вывода.

::: sql
Сравнение с SQL.
:::

Другие блоки: `::: note`, `::: tip`, `::: warn` (частая ошибка), `::: deep` (для любопытных). Свой заголовок: `::: warn Осторожно с запятыми`.

## Практика

## task: id-задачи | Название | warmup
Условие (Markdown).
### starter
```python
заготовка в редакторе
```
### setup
```python
скрытый код перед кодом ученика (необязательно)
```
### check
```python
assert need('revenue') == 26600, 'Понятное сообщение: что не так и куда смотреть.'
```
### hint
Первая подсказка (подсказок может быть несколько — открываются по одной).
### solution
```python
эталон
```
### explain
Необязательный разбор — показывается после решения.
```

Уровни: `warmup` (разминка), `base` (база), `plus` (посложнее), `star` (со звёздочкой — по желанию, в прогресс урока не входит). В уроке 7–10 задач: 2–3 разминки, 3–4 базовых, 1–2 посложнее, 1 со звёздочкой.

## Стандарт подробности (с 07.10.2026, по замечанию «курс недостаточно подробный»)

**Теория — каждое новое понятие по лестнице:**

1. *Зачем* — какой рабочий вопрос «Зерна» без него не решить (1–2 фразы).
2. *Интуиция* — бытовая аналогия или аналогия с SQL/Excel (`::: sql`).
3. *Игрушечный пример руками* — 3–6 чисел, каждый шаг вычисления выписан словами и цифрами, потом то же кодом. Формулы — только после примера, каждый символ расшифрован.
4. *На реальных данных* — живой пример на файле урока.
5. *Разбор кода* — под каждым нетривиальным примером список «Что здесь происходит»: по пункту на ключевую строку (что делает, какая форма/тип получается). В самом коде — комментарии к неочевидным строкам.
6. *Что получилось* — как читать вывод: какие числа важны и что они значат для бизнеса.
7. *Типичные ошибки* — `::: warn` с конкретной ошибкой, её сообщением или симптомом и исправлением.

В уроке 2–3 «Предскажите вывод» и хотя бы один промежуточный пример между теорией и задачами («Разберём вместе»: задача, ход решения по шагам, код).

**Задачи — 9–11 в уроке:** 2–3 разминки (одна — «собери код»), 4–5 базовых (по одному навыку на задачу, маленькими шагами), 2 посложнее, 1 со звёздочкой.

**Подсказки — 2–3 на задачу, от общего к конкретному:** 1) какую идею/шаг применить; 2) какая функция и с какими аргументами; 3) почти готовый код с пропусками `...`. У звёздочки — 3.

**Разбор (`### explain`) — у каждой задачи уровня base и выше:** почему решение такое, что значит результат, типичная ошибка и как её заметить (что было бы, если …).

**Сообщения проверок** — называют, что не так, и намекают, куда смотреть, не раскрывая ответ.

## Подача: обязательные элементы урока (с 08.10.2026)

- **«Проверьте себя»** — минимум один вопрос на понимание в теории каждого урока. Ровно один верный вариант, у **каждого** варианта своё объяснение (почему верно или почему нет):

  ```text
  ::: quiz
  Вопрос?

  - [x] Верный вариант
    > Почему верно.
  - [ ] Неверный вариант
    > Почему не подходит.
  :::
  ```

  Сборщик падает, если верных вариантов не один или у варианта нет объяснения. Числа в вопросах — из урока или посчитаны кодом.
- **Связь теории и задач** — в конце раздела строка `{{practice: id1, id2}}` (id задач этого урока). На странице она превращается в «Потренироваться — задачи: …», а в задаче появляется ссылка «↑ К теории: раздел». Каждая задача урока (кроме проектов) привязана к одному разделу — к тому, где объяснено нужное ей.
- **Схемы** — `::: figure имя` + подпись + `:::`. SVG лежит в `content/figures/имя.svg` и вставляется в страницу целиком. Цвета — только классами (`ink`, `ink2`, `mut`, `acc`, `ok`, `err`, `warn`, `box`, `box-acc`, `box-ok`, `box-err`, `box-warn`, `ln`, `ln-acc`, `ln-ok`, `ln-err`, `ln-mut`, `dash`, `sm`, `b`), тогда схема сама меняется в тёмной теме. Ширина viewBox — около 700, шрифт 12–14; на телефоне схема прокручивается вбок. Все числа на схеме — из урока или посчитаны кодом; условную схему так и подписывать.
- **Варианты в «Проверьте себя» перемешиваются** на странице (свой порядок у каждого вопроса, стабильный между заходами), поэтому в исходнике верный вариант можно писать где угодно.
- **Рамка главы** — два необязательных файла в папке главы:
  - `intro.md` → страница «О главе» (`chNN/index.html`). В шапке `question` (бизнес-вопрос главы, обычно из её проекта) и `learn` (список «Чему вы научитесь»; строки с двоеточием брать в кавычки). Ниже — 2–3 абзаца о главе. Число уроков, задач и время сборщик считает сам.
  - `test.md` → «Итоговый тест главы» (`chNN/test.html`): 8–10 блоков `::: quiz id-урока` (тот же формат, что «Проверьте себя», плюс id урока после `quiz`). Вопросы — на понимание, по всей главе, не повторяют вопросы уроков. В конце теста — итог «X из N», ссылки на уроки по неверным ответам и новая попытка.
  - Страницы встают в оглавление и в навигацию: «О главе» → урок 1 → … → последний урок → тест → следующая глава.
- **Второй «Проверьте себя»** — в тяжёлых уроках (статистика, метрики, переобучение, градиент, нейросети и т. п.) ещё один вопрос во второй половине теории, по другому понятию, чем первый.
- **Формулы** — KaTeX, локально (`site/assets/vendor/katex/`): в строке `$\sigma$`, отдельной строкой `$$SE = \frac{\sigma}{\sqrt{n}}$$`. Формула идёт после игрушечного примера, и под ней каждый символ расшифрован словами. Внутри кода и `` `…` `` доллары не трогаются. Стили и скрипт KaTeX подключаются только на страницах с формулами.
- **Аналогия** — одна бытовая аналогия на трудное понятие, блоком `::: tip Аналогия` (2–4 фразы, из жизни, без новых терминов; где аналогия хромает — сказать одной фразой).
- **Виджеты** — `::: widget имя` + подпись + `:::`. Данные — `content/widgets/имя.json` (для `threshold` и `tree-depth` пересчитываются `uv run tools/gen_widgets.py` на данных уроков; у `gd-lr` пять точек урока зашиты в код), код — `site/assets/widgets.js` (подключается только там, где есть виджет). Сейчас есть: `gd-lr` (шаг градиентного спуска), `threshold` (порог классификации и матрица ошибок), `tree-depth` (глубина дерева, обучение против теста). Новый виджет — функция в `widgets.js` и имя в `WIDGETS` в `tools/build.py`.

## Другие форматы

**Предскажите вывод** — в теории, перед запуском примера:

````markdown
::: predict
```python static
print(7 // 2, 7 % 2)
```

- `3.5 1`
- [x] `3 1`
- `3 0.5`

Почему: `//` — целая часть от деления, `%` — остаток.
:::
````

Ровно один вариант с `[x]`. Многострочный вывод пишется через ` | ` (`10 | None`). Ответ «код упадёт» — `` `Ошибка TypeError` ``. `verify.mjs` сверяет правильный вариант с настоящим выводом кода.

**Собери код из строк** — задача, у которой вместо `### starter` раздел `### parsons` с правильным кодом (с отступами). Строки перемешиваются автоматически, проверка — обычная `### check` (порядок, при котором код работает верно, тоже засчитывается). Обычно это разминка.

**Контрольная точка** — `content/<глава>/exam-N.md` с `mode: exam` в шапке и `exams:` у главы в `course.yaml` (`after:` — после какого урока). Четвёртое поле заголовка задачи — урок, к которому она относится: `## task: id | Название | base | 04-lists`. По нему строится «Что повторить».

**Понятно объяснено?** — добавляется автоматически в конце каждого раздела `##`. Отчёт для правки уроков: `uv run tools/hard_spots.py`.

## Помощники в проверках

| | |
|---|---|
| `need('x', int)` | переменная из кода ученика; понятная ошибка, если её нет или тип не тот |
| `_out`, `_lines` | весь вывод; непустые строки вывода без пробелов по краям |
| `_code` | текст кода ученика |
| `printed(t)`, `printed_line(t)` | `t` встречается в выводе / есть строка вывода, равная `t` |
| `calls('round')` | сколько раз вызвана функция или метод |
| `has_literal(26600)` | значение вписано в код руками (ловим «подгонку ответа») |
| `uses_fstring()` | в коде есть f-строка |
| `close(a, b, tol)` | числа равны с точностью `tol` |
| `ax_of(i=0)` | оси i-го графика, нарисованного кодом ученика (понятная ошибка, если графика нет) |
| `figs` | список нарисованных полотен (`Figure`) |

Сообщения в `assert` пишем как живой наставник: что получилось, что ожидалось и куда посмотреть. Не раскрываем решение целиком.

Проверка графиков — по объектам matplotlib: `ax.get_title()`, `ax.get_xlabel()`, `ax.patches` (столбцы; `get_height()` / `get_width()`), `ax.lines` (`get_ydata()`), `ax.collections` (точки scatter), `ax.get_xticklabels()`, `ax.get_legend()`, `ax.texts` (подписи `bar_label`).

## Практика в Jupyter (`site/notebooks/`)

Те же задачи, что на сайте, решаются и в своём Jupyter — с той же проверкой. Всё лежит в `site/notebooks/` и попадает в архив курса (`tools/pack.py`; рабочая папка `_work` и `.ipynb_checkpoints` — нет).

| Файл | Что это |
|---|---|
| `chNN-practice.ipynb` | практикум главы: по разделу на урок, у каждой кодовой задачи — markdown с условием и ячейка `%%task глава/урок/id` с заготовкой. Задачи «собери код из строк» остаются на сайте; задачи контрольной точки — отдельным разделом (проверка говорит только «верно/нет») |
| `tasks/chNN.json` | проверки, подготовка (`setup`), подсказки, решения и разборы задач главы — для `dsc.py` |
| `dsc.py` | расширение IPython: `%load_ext dsc` |
| `requirements.txt` | библиотеки для блокнотов — те же версии, что у Pyodide на сайте |
| `project-template.ipynb` | шаблон проектного блокнота |
| `check_notebook.py` | самопроверка проектного блокнота перед ревью |

**Генерация.** Блокноты и `tasks/*.json` — производные от уроков, руками их не правят:

```sh
python3 tools/make_notebooks.py
```

Скрипт берёт уроки через `load_course()` из `tools/build.py` (тот же разбор, что у сайта), пишет все 15 практикумов, файлы проверок и шаблон проекта. Запуск идемпотентный: файл переписывается, только если изменилось содержимое. Id ячеек стабильные (хэш адреса задачи), поэтому diff в git — только по сути. После правки уроков — перегенерировать.

**Расширение `dsc`.** Блокнот открывается из `site/notebooks` (там лежит `dsc.py`). `%load_ext dsc`:

- копирует `site/data` в `site/notebooks/_work` (только изменившиеся файлы) и делает её текущей папкой: `pd.read_csv('orders.csv')` работает, как на сайте, а файлы, которые пишет код ученика, не портят данные курса. Перед каждой задачей копии файлов курса сверяются с `site/data` (размер и время изменения): если код перезаписал, скажем, `orders.csv`, исходный файл возвращается — как на сайте, где каждый запуск получает свежие файлы;
- подключает `site/assets/harness.py` — тот же файл, что в браузере, — но не даёт ему включить бэкенд `Agg`: графики показываются под ячейкой (inline);
- регистрирует магию `%%task глава/урок/id`.

Ячейка `%%task` работает так: выполняется `setup` задачи (если есть), затем код ячейки — в пространстве имён блокнота, поэтому переменные остаются для следующих ячеек. Вывод виден сразу и одновременно копится для проверки. Последнее выражение показывается, как в обычной ячейке. `plt.show()` внутри задачи откладывается до конца проверки (в Jupyter он закрывает график, а проверке нужны `ax_of()` и `figs`). Затем запускается `### check` с теми же помощниками, что в браузере (`need`, `printed`, `_out`, `_lines`, `_code`, `calls`, `has_literal`, `close`, `ax_of`, `figs`), и под ячейкой появляется «✓ Верно» или сообщение проверки. Ошибка в коде показывается тем же понятным текстом, что на сайте; номера строк совпадают с ячейкой (строка 1 — `%%task`). Магии и `!`-команды внутри ячейки тоже работают.

Помощники в блокноте: `dsc.hint('id')` — следующая подсказка (`dsc.hint('id', 2)` — конкретная), `dsc.solution('id', sure=True)` — эталон и разбор (без `sure=True` только просьба подтвердить), `dsc.progress()` — что решено в этом сеансе, `dsc.tasks('ch03')` — адреса задач главы, `dsc.check_project('ch04/09-project')` — сверка проектного блокнота с эталонами (ниже). Короткий id подходит, если он не повторяется в других уроках; иначе — полный адрес.

**Сверка проекта с эталонами** (`dsc.check_project('глава/урок')`, её же вызывает `check_notebook.py --project`). Проверяет переменные, которые уже посчитал блокнот, всеми проверками задач урока из `tasks/chNN.json` — с той же семантикой, что `%%task`, но без запуска кода задач:

- рабочая папка — `_work` (данные курса, как у `%%task`); файлы, которые задача создаёт сама (см. ниже), копируются туда из папки блокнота — проверка не увидит файл от прошлых запусков;
- `setup` задачи выполняется в отдельном пространстве имён: то, что задача получает готовым, берётся из подготовки (эталон), а имена, которые создаёт или меняет эталон (присваивание, `df['x'] = …`), — из блокнота; `need()` ищет в блокноте;
- `### check` выполняется по инструкциям верхнего уровня. Инструкции с помощниками, которым нужна ячейка задачи (`_out`, `_lines`, `printed`, `printed_line` — печать; `_code`, `calls`, `uses_fstring`, `has_literal` — код; `ax_of`, `figs` — график), и всё, что зависит от их результатов, пропускаются. Итог задачи: ✓ (всё сошлось), ✓ «значения верны; не проверено: нужен вывод ячейки (график)», ✗ с сообщением проверки, «– не проверено: нужен вывод ячейки (…)» — если без ячейки проверить нечего;
- если не сошлась инструкция проверки, которая читает (сама или через посчитанные из неё в проверке значения) переменную этой задачи, а переменная есть в блокноте и ниже по уроку её снова создаёт другая задача, итог — «не проверено: … позже пересчитывает задача …»: в блокноте осталось только последнее значение. Несовпадение в другой переменной той же задачи и отсутствующая переменная — обычный ✗. Отсюда правило для авторов проектов: **у каждой задачи урока-проекта — свои имена переменных-результатов**, и значения проверяются через `need()`, а не только через вывод или график.

Что это значит для авторов задач:

- проверка должна проходить и в «настоящем» Python (версии из `requirements.txt`), а не только в Pyodide. Код только для браузера (`js`, `pyodide`) в задачи не ставим;
- в блокноте переменные живут между ячейками. Чтобы ячейка с пустым или неверным кодом не прошла на значении от прошлой удачной попытки, `dsc` перед запуском задачи удаляет из пространства имён её переменные-результаты: имена, которым эталон присваивает значение на верхнем уровне и которые упоминаются в `### check` (как имя или строкой, `need('total')`). Остальные переменные блокнота не трогаются, `setup` выполняется уже после очистки. Отсюда правило: результат задачи создаёт сам код ячейки (как на сайте), и проверка всё равно сверяет значение, а не только наличие — переменная с тем же именем могла остаться от другой задачи;
- задача, которая пишет файл, оставляет его в `_work`. Перед запуском задачи `dsc` удаляет из `_work` файлы, которые она должна создать сама: имя есть строкой в `### check` и в эталоне, но его нет в `setup` и в `site/data`. Иначе файл от прошлой удачной попытки засчитал бы неверный код. Поэтому имя создаваемого файла пишите в проверке буквально (`'report.md'`, не через переменную) и всё равно проверяйте содержимое, а не только `os.path.exists`.

**Шаблон проекта** (`project-template.ipynb`). Первая ячейка — импорты, версии библиотек, `RANDOM_STATE`, относительный путь `DATA = Path('../data')`. Разделы: `## 1. Цель` → `## 2. Данные` → `## 3. Предобработка` → `## 4. Анализ и модели` → `## 5. Выводы и рекомендации`. После каждого раздела с кодом — markdown «Вывод по …». Врезка сверху объясняет, как работать с шаблоном (в том числе: переменные называть как в задачах проекта и запускать `python check_notebook.py my.ipynb --project chNN/<урок>`), и содержит чек-лист самопроверки. Места для своего текста помечены ✎. Пример кода — на `daily_sales.csv`, он выполняется сверху вниз. Шаблон генерирует тот же `tools/make_notebooks.py` (список `TEMPLATE`).

**Самопроверка** (`check_notebook.py`, нужны `nbformat`, `nbclient`, `ipykernel`):

```sh
python check_notebook.py проект.ipynb                 # статические проверки + запуск с чистого ядра
python check_notebook.py проект.ipynb --timeout 1800  # долгое обучение
python check_notebook.py проект.ipynb --no-run        # без запуска
python check_notebook.py проект.ipynb --project ch04/09-project                    # + сверка с эталонами урока
python check_notebook.py проект.ipynb --project ch02/09-project --course ПАПКА_КУРСА  # блокнот вне папки курса
```

Скрипт выполняет копию блокнота с чистого ядра (`python3` текущего окружения, папка — папка блокнота) и сообщает по-русски:

- ошибки при запуске: первую — подробно, следующие — списком, они часто вызваны первой;
- запуск ячеек не по порядку (по сохранённым `In [n]`) и незапущенные ячейки;
- абсолютные пути в строках кода (`C:\…`, `/Users/…`, `/home/…`, `~/…`);
- закомментированный код — строки `# …`, которые разбираются как Python;
- разделы `## …`, где после последней ячейки кода нет markdown-вывода;
- нет `RANDOM_STATE` в первой ячейке при наличии случайности, `random_state=` числом, импорты не в начале;
- оставшиеся пометки ✎ шаблона и предупреждения (`Warning`) в выводе;
- с `--project глава/урок` — после запуска в том же ядре выполняется добавленная последней ячейка с `dsc._project_json(...)`: по каждой задаче урока ✓ / ✗ с сообщением проверки и сводка «Совпало с эталоном: n из N». Несовпадения попадают в «Надо исправить», задачи, которые без своей ячейки не проверить, — в «Стоит посмотреть». Папку курса (`site/notebooks` с `dsc.py` и `tasks/`) скрипт ищет рядом с собой и с блокнотом и выше по папкам; иначе — `--course` (папка архива курса или её `site/notebooks`). В уроках-проектах со сдачей блокнотом стоит готовая команда для своего урока.

Код возврата 1, если есть пункты «Надо исправить». После скрипта — ревью навыком ds-project-review.

**Проверка инфраструктуры** (после изменений в `dsc.py`, `harness.py` или генераторе) — каждый практикум выполняется через nbclient дважды: с эталонами вместо заготовок (все задачи обязаны дать «✓ Верно») и с заготовками (ни одна не должна пройти, магия не должна падать). Нужны `nbclient` и `ipykernel` с библиотеками из `requirements.txt`; долго (глава 14 — несколько минут):

```sh
python3 tools/make_notebooks.py --test solution          # все главы
python3 tools/make_notebooks.py --test starter ch03 ch05 # выборочно
```

Блокноты при этом не меняются: выполняются копии в памяти. Код возврата 1, если есть проблемы. Прогон идёт на установленных в системе версиях библиотек; `requirements.txt` закрепляет версии Pyodide, поэтому перед выпуском полезен и прогон в окружении из `requirements.txt` (`uv run --with-requirements site/notebooks/requirements.txt python3 tools/make_notebooks.py --test solution`).

## Перед коммитом

```sh
uv run tools/build.py --export build/tasks.json && node tools/verify.mjs build/tasks.json
python3 tools/make_notebooks.py
uv run tools/build.py
```

`verify.mjs` прогоняет каждую задачу: эталон обязан пройти проверку, заготовка — нет; каждый пример в теории обязан выполниться (или упасть, если помечен `error`). `make_notebooks.py` обновляет блокноты Jupyter: без него в них останутся старые задачи. `build.py` берёт число задач для блока «Практика в Jupyter» на страницах глав из готовых блокнотов, поэтому блокноты генерируются до сборки сайта.

## Дополнительные блокноты (site/notebooks/extra)

Блокноты для тем, которые в браузере не запускаются: CatBoost и LightGBM (ch10), PyTorch на табличных данных (ch11), лемматизация pymorphy3 и transformers (ch13); плюс блокнот по Excel (ch03) — для работы в своём Jupyter (в браузере Excel тоже работает: openpyxl лежит в локальном Pyodide, `runner.js` подгружает его сам, если в коде есть `read_excel`/`to_excel`). Их зависимости — в `site/notebooks/extra/requirements-extra.txt`, ставятся отдельно: `uv pip install -r site/notebooks/extra/requirements-extra.txt`. Данные берутся из `site/data`. Блокнот `ch13-transformers.ipynb` нужно один раз выполнить на машине с интернетом (скачивается модель) — выводы в нём пока ожидаемые, а не полученные.

## Основной путь и углубление

В `course.yaml` у урока основного пути стоит `core: true` (≈ 106 ч: Python, pandas и SQL, git, очистка, EDA, статистика и A/B, первые модели, метрики, деньги, артефакт модели и два обязательных проекта — итоговый главы 8 и финальный главы 15). Остальные уроки — углубление: на сайте у них пометка «углубл.», в оглавлении и списках есть фильтр «Только основной путь» (localStorage `dsc-core-only`), на главной — прогресс по основному пути. Урок основного пути не должен опираться на уроки-углубления: если опирается — либо перенести нужное в основной урок, либо пометить зависимость `core: true`.
