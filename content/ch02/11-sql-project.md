## Задача

> Полгода назад, 1 марта 2026 года, мы запустили карту гостя: на кассе или в приложении. Ещё были три акции: «Весенний раф» в апреле, скидка для приложения в июне и «Лимонадное лето» в июле–августе. Разберитесь, что это нам дало. Как росла выручка по городам? Приходят ли гости с картой чаще и тратят ли больше? Кто удерживается лучше — гости из приложения или с кассы? Сработали ли акции и что они стоили по марже? И проверьте меню: мне кажется, там есть позиции, которые никто не покупает.

Это типичная задача аналитика на рабочей базе. Данных много, и они лежат не в одном CSV, а в нескольких таблицах, которые надо правильно соединить. Половина ошибок в таких проектах — не в формулах, а в соединениях: заказ, размноженный позициями, или гость, потерянный во внутреннем JOIN.

## Данные: схема базы

База «Зерна» за март–август 2026 года. Она лежит в двух видах: шесть CSV-файлов `zdb_*.csv` — для DuckDB в браузере — и один файл SQLite `zerno.db` с теми же таблицами (позиции заказов там называются `order_items`).

| таблица | одна строка — это | ключ | строк | важные столбцы |
|---|---|---|---|---|
| `shops` | кофейня | `shop_id` | 6 | `city`, `name`, `seats` |
| `menu` | позиция меню | `item_id` | 15 | `name`, `category`, `price` (по меню), `cost` (себестоимость) |
| `guests` | гость с картой | `guest_id` | 1510 | `reg_date`, `source` (касса / приложение), `home_shop_id` |
| `promos` | акция | `promo_id` | 3 | `start_date`, `end_date`, `discount_pct`, `item_id` (пусто — скидка на весь чек) |
| `orders` | заказ | `order_id` | 14 510 | `guest_id` (пусто — без карты), `shop_id`, `ordered_at`, `channel`, `promo_id` |
| `items` | позиция заказа | `order_id` + `item_id` | 22 813 | `qty`, `price` (фактическая цена с учётом скидки) |

Связи: `orders.shop_id → shops`, `orders.guest_id → guests`, `orders.promo_id → promos`, `items.order_id → orders`, `items.item_id → menu`. Главная таблица фактов — `items`: выручка и маржа живут в ней, а всё остальное — справочники и «шапки» заказов.

::: figure db-schema
Шесть таблиц базы и ключи между ними. Каждая стрелка идёт от «многих» к «одному»: много позиций — к одной позиции меню и одному заказу, много заказов — к одной кофейне, одному гостю и одной акции. Пунктир и подписи «пусто» — связи, которых у заказа может не быть: без карты нет `guest_id`, без акции — `promo_id`.
:::

::: sql
Это обычная схема «звезда», как в любом DWH: факты (`items`) и измерения (меню, кофейни, гости). Если вы строили витрины в SQL Server или модели в SSAS, правило то же: агрегировать факты на нужном зерне и только потом присоединять измерения.
:::

В браузере загрузим шесть файлов в DuckDB как **таблицы** — один раз, дальше к ним обращаются по имени, как к таблицам рабочей базы:

```python
import duckdb
import pandas as pd

dates = {"orders": ["ordered_at"], "guests": ["reg_date"], "promos": ["start_date", "end_date"]}
for name in ["shops", "menu", "guests", "promos", "orders", "items"]:
    t = pd.read_csv(f"zdb_{name}.csv", parse_dates=dates.get(name, []))
    duckdb.sql(f"CREATE OR REPLACE TABLE {name} AS SELECT * FROM t")   # t — датафрейм из строки выше

duckdb.sql("""
    SELECT o.order_id, o.ordered_at, s.city, m.name, i.qty, i.price
    FROM orders AS o
    JOIN items AS i USING (order_id)
    JOIN shops AS s USING (shop_id)
    JOIN menu  AS m USING (item_id)
    ORDER BY o.ordered_at
    LIMIT 5
""").df()
```

Что здесь происходит:

- `pd.read_csv(..., parse_dates=...)` читает файл, а столбцы с датами сразу превращает в даты: в SQL с ними будут работать `date_trunc` и `date_diff`.
- `CREATE OR REPLACE TABLE orders AS SELECT * FROM t` копирует датафрейм `t` в таблицу DuckDB с постоянным именем `orders`. Переменная `t` на следующем шаге цикла перезапишется, а таблица останется. `OR REPLACE` позволяет запускать ячейку повторно без ошибки «уже существует».
- Имя таблицы подставлено f-строкой — и это нормально: имена таблиц и столбцов через `params=` не передаются, заполнители работают только для **значений**. Главное, что имена берутся из нашего же списка, а не из ввода пользователя.
- `USING (order_id)` — краткая запись `ON o.order_id = i.order_id`, когда столбец называется одинаково в обеих таблицах.

::: deep Почему не `FROM 'zdb_orders.csv'` и не `VIEW`
Можно было бы обращаться к файлу прямо в запросе или создать представление `CREATE VIEW orders AS SELECT * FROM 'zdb_orders.csv'` — сохранённый запрос с именем. Но представление не хранит данные: при каждом запросе DuckDB заново читает файл и угадывает типы столбцов. На своём компьютере это незаметно, а в браузере на 14 тысячах строк — секунды на каждый запрос. Таблица загружается в память один раз. На работе выбор тот же: представления — для «живых» данных, таблицы (материализация) — когда к одним и тем же данным много запросов.
:::

Тот же вопрос к базе SQLite — через `sqlite3` и `pd.read_sql_query`, как в уроке про DuckDB. Обратите внимание на диалект: месяц в SQLite — `strftime('%Y-%m', ...)`, а окна работают так же.

```python
import sqlite3
import pandas as pd

con = sqlite3.connect("zerno.db")
monthly = pd.read_sql_query("""
    SELECT strftime('%Y-%m', o.ordered_at) AS month,
           SUM(i.qty * i.price) AS revenue,
           ROUND(100.0 * SUM(i.qty * i.price) / SUM(SUM(i.qty * i.price)) OVER (), 1) AS pct
    FROM orders AS o
    JOIN order_items AS i ON i.order_id = o.order_id
    GROUP BY month
    ORDER BY month
""", con)
con.close()
monthly
```

Как читать результат: за полгода сеть заработала 4.85 млн ₽. Март — самый слабый месяц (582 500 ₽, 12.0 % полугодия), с мая выручка держится около 870–890 тысяч в месяц. Почему март так отстаёт — один из вопросов проекта.

### Две ловушки соединений

Зачем: в базе из нескольких таблиц ошибки прячутся не в формулах, а в соединениях. Соединение может **размножить** строки: одна строка заказа превращается в несколько строк позиций. А может **потерять** их: строка, у которой нет пары, исчезает. Ни то ни другое не вызывает ошибку — меняются только цифры.

::: tip Аналогия
Кассовый чек: покупка одна, а строк в чеке три. Если считать покупки по строкам чеков, их окажется втрое больше. Где аналогия хромает: в базе «строки чека» лежат в отдельной таблице, и размножение происходит только в момент соединения.
:::

**Размножение — игрушечный пример руками.** Два заказа: Z1 — два капучино по 190 ₽ и круассан за 140 ₽, Z2 — один латте за 210 ₽.

1. В «шапках» 2 строки, в позициях — 3. После соединения по `order_id` строк 3: заказ Z1 повторился дважды, по разу на каждую свою позицию.
2. `COUNT(*)` даёт 3 — это позиции. Заказов — `COUNT(DISTINCT order_id)` = 2.
3. `AVG(qty * price)` по этим строкам: (380 + 140 + 210) / 3 ≈ 243.3 ₽. Это средняя **позиция**.
4. Средний **чек** считают в два шага: сначала сумма каждого заказа (Z1 = 380 + 140 = 520, Z2 = 210), потом среднее: (520 + 210) / 2 = 365 ₽.

::: figure items-grain
Слева «шапки» заказов, справа — они же после соединения с позициями: строк столько, сколько позиций. `COUNT(*)` считает позиции, заказы — только `COUNT(DISTINCT order_id)`. Внизу — средний чек: среднее по строкам позиций даёт среднюю позицию, настоящий чек — среднее сумм по заказам. В базе «Зерна» разница — 212.5 ₽ против 334.1 ₽.
:::

```python
import duckdb
import pandas as pd

t_orders = pd.DataFrame({"order_id": ["Z1", "Z2"], "channel": ["зал", "с собой"]})
t_items = pd.DataFrame({"order_id": ["Z1", "Z1", "Z2"],
                        "item": ["Капучино", "Круассан", "Латте"],
                        "qty": [2, 1, 1], "price": [190, 140, 210]})
print(duckdb.sql("""
    SELECT COUNT(*) AS lines, COUNT(DISTINCT order_id) AS orders_n,
           ROUND(AVG(i.qty * i.price), 1) AS avg_line
    FROM t_orders AS o
    JOIN t_items AS i USING (order_id)
""").df())
print(duckdb.sql("""
    WITH t AS (                                  -- шаг 1: сумма каждого заказа
        SELECT order_id, SUM(qty * price) AS total
        FROM t_items
        GROUP BY order_id
    )
    SELECT AVG(total) AS avg_check FROM t        -- шаг 2: среднее по заказам
""").df())
```

Что здесь происходит:

- Первый запрос соединяет «шапки» с позициями и считает на получившихся строках: 3 строки, 2 разных заказа, средняя строка — 243.3 ₽.
- Второй запрос сначала сворачивает позиции до заказов в CTE `t` — по строке на заказ, — и только потом берёт среднее: 365 ₽. Соединять с «шапками» для этого даже не нужно: сумма заказа целиком живёт в позициях.

Как читать результат: правило «агрегировать факты до нужного зерна, потом соединять» спасает от обеих ошибок. «Зерно» — это то, чем является одна строка: позиция, заказ, гость. Перед каждым `COUNT` и `AVG` спросите себя, какое зерно у таблицы сейчас.

**Потеря и поиск «чего нет».** Вопрос шага 3 — какие позиции меню ни разу не продавались. Внутреннее соединение меню с позициями такие строки просто выбросит: у них нет пары. Нужен `LEFT JOIN`. Он сохраняет все строки меню, а у позиций без продаж столбцы правой таблицы заполняет `NULL`. Остаётся оставить строки, где справа `NULL`: `WHERE i.item_id IS NULL`. Такой приём называют **антисоединением**.

Игрушечный пример руками: в меню капучино, лимонад и матча; капучино продан в трёх заказах, лимонад — в двух, матча — ни разу.

1. `LEFT JOIN` даёт 3 + 2 строки проданных позиций и одну строку матчи с `NULL` справа — всего 6.
2. `WHERE i.item_id IS NULL` оставляет одну строку — матчу.
3. Если вместо этого написать условие на правую таблицу, например `WHERE i.qty > 0`, для строки матчи оно даст «неизвестно» (`NULL > 0`), и строка пропадёт. Останутся только проданные позиции — ровно как после внутреннего соединения.

::: figure anti-join
То же на трёх позициях настоящего меню «Зерна». У проданных позиций после `LEFT JOIN` по строке на каждую продажу (у капучино — 3 509, у лимонада — 1 224), а у позиции без продаж одна строка с `NULL` справа. Фильтр `IS NULL` оставляет именно её. Условие `qty > 0` на правую таблицу отбрасывает строку с `NULL`, и непроданной позиции в результате уже нет: `LEFT JOIN` молча стал внутренним.
:::

```python
import duckdb
import pandas as pd

t_menu = pd.DataFrame({"item_id": ["M03", "M10", "M09"],
                       "name": ["Капучино", "Лимонад", "Матча"]})
t_items = pd.DataFrame({"order_id": ["Z1", "Z2", "Z3", "Z4", "Z5"],
                        "item_id": ["M03", "M03", "M10", "M03", "M10"],
                        "qty": [1, 2, 1, 1, 3]})
unsold = duckdb.sql("""
    SELECT m.name
    FROM t_menu AS m
    LEFT JOIN t_items AS i USING (item_id)
    WHERE i.item_id IS NULL            -- пары справа нет
""").df()
broken = duckdb.sql("""
    SELECT DISTINCT m.name
    FROM t_menu AS m
    LEFT JOIN t_items AS i USING (item_id)
    WHERE i.qty > 0                    -- условие на правую таблицу
    ORDER BY m.name
""").df()
print(unsold["name"].tolist())
print(broken["name"].tolist())
```

Что здесь происходит: первый запрос находит матчу — единственную позицию без пары. Второй возвращает капучино и лимонад: строка матчи с `NULL` не прошла `qty > 0`, и от `LEFT JOIN` ничего не осталось. Если условие на правую таблицу всё же нужно (например, считать только продажи в зале), его ставят в `ON`: `LEFT JOIN t_items AS i ON i.item_id = m.item_id AND i.qty > 0`. Тогда оно отбирает пары, а не строки результата.

::: warn Типичные ошибки
- **Столбец «шапки» после соединения с позициями.** Любое поле заказа — канал, скидка на весь чек — после `JOIN` стоит в каждой позиции. `SUM` по нему умножится на число позиций. Сверните позиции до заказа в CTE и только потом соединяйте.
- **`COUNT(*)` после `LEFT JOIN`.** У позиции без продаж остаётся одна строка с `NULL`, и `COUNT(*)` насчитает ей одну продажу. `COUNT(i.order_id)` пропускает `NULL` и даст 0.
- **Нет сверки строк.** После каждого соединения сравните число строк с ожидаемым: «шапки» × позиции = число позиций, `LEFT JOIN` к справочнику не меняет число строк слева. Расхождение — признак размножения или потери.
:::

## Разберём вместе: когорты руками

Зачем: вопрос «кто удерживается лучше» нельзя решить средним числом заказов на гостя. Гость, пришедший в марте, мог заказывать полгода, а гость из августа — от силы месяц, и в среднем по всем «старые» гости всегда выглядят лучше. Честное сравнение — по **когортам**: гостей группируют по месяцу первого заказа и следят за каждой группой отдельно, отсчитывая месяцы от её старта.

::: tip Аналогия
Когорта — как выпуск школы. Сравнивать, сколько выпускников 2015 и 2024 года уже окончили вуз, бессмысленно: у вторых ещё не было времени. Сравнивают «через 5 лет после выпуска» у каждого выпуска. Где аналогия хромает: гость, в отличие от выпускника, может «вернуться» через месяц отсутствия.
:::

Пять гостей и их заказы по месяцам:

| гость | заказы | первый заказ — когорта |
|---|---|---|
| A | март, апрель, май | март |
| B | март | март |
| C | март, май | март |
| D | апрель, апрель | апрель |
| E | апрель, май | апрель |

1. **Когорта «март»** — A, B, C: 3 гостя. Месяц k = 0 — март, 3 из 3 = 100 %.
2. k = 1 — апрель: заказал только A. Удержание 1 / 3 ≈ 33.3 %.
3. k = 2 — май: заказали A и C. Удержание 2 / 3 ≈ 66.7 %. Оно **выросло**: C пропустил апрель, но вернулся. Удержание здесь — «заказал в этом месяце», а не «заказывал каждый месяц подряд».
4. **Когорта «апрель»** — D и E: 2 гостя. Два апрельских заказа D — это один активный гость в апреле, а не два. k = 1 — май: только E, 1 / 2 = 50 %.
5. k = 2 для апрельской когорты — это июнь, а данных за июнь в примере нет. Клетка **пустая**, а не нулевая.

::: figure cohort-sql
Слева — заказы пяти гостей по месяцам; цвет — когорта, точка в кружке — первый заказ, подпись k — месяц от старта когорты. Справа — то, что из этого соберёт запрос ниже: активные гости и удержание по клеткам «когорта × k». Два апрельских заказа D дают одного активного гостя, а клетка «апрель, k = 2» пустая: июня в данных нет.
:::

```python
import duckdb
import pandas as pd

toy = pd.DataFrame({
    "guest": ["A", "A", "A", "B", "C", "C", "D", "D", "E", "E"],
    "month": ["2026-03-01", "2026-04-01", "2026-05-01", "2026-03-01", "2026-03-01",
              "2026-05-01", "2026-04-01", "2026-04-01", "2026-04-01", "2026-05-01"],
})
toy["month"] = pd.to_datetime(toy["month"])
duckdb.sql("""
    WITH first AS (                       -- шаг 1: когорта гостя = месяц первого заказа
        SELECT guest, MIN(month) AS cohort FROM toy GROUP BY guest
    ),
    active AS (                           -- шаг 2: в каких месяцах (от старта когорты) гость заказывал
        SELECT DISTINCT t.guest, f.cohort, date_diff('month', f.cohort, t.month) AS k
        FROM toy AS t JOIN first AS f USING (guest)
    ),
    counts AS (                           -- шаг 3: активные гости когорты в месяце k
        SELECT cohort, k, COUNT(*) AS guests FROM active GROUP BY cohort, k
    )
    SELECT cohort, k, guests,
           ROUND(100 * guests / FIRST_VALUE(guests) OVER (PARTITION BY cohort ORDER BY k), 1) AS pct
    FROM counts
    ORDER BY cohort, k
""").df()
```

Что здесь происходит:

- `first` — по строке на гостя: его когорта.
- `active` — `DISTINCT` убирает повторные заказы в одном месяце (два апрельских заказа D). `date_diff('month', cohort, month)` — номер месяца от старта: 0, 1, 2…
- `counts` — сколько гостей когорты были активны в месяце k.
- `FIRST_VALUE(guests) OVER (PARTITION BY cohort ORDER BY k)` — размер когорты (строка k = 0), поставленный в каждую строку когорты. Деление на него даёт удержание. Здесь рамка по умолчанию безопасна: первая строка рамки — всегда k = 0.

Как читать результат: 100, 33.3, 66.7 — у мартовской, 100 и 50 — у апрельской, как и посчитали руками. В шаге 9 этот же запрос — на настоящих гостях.

На настоящих гостях таблица «когорта × k» получается треугольником. Мартовскую когорту наблюдали шесть месяцев, августовскую — один: данные кончаются 31 августа. Тот же правый край встретится и в шаге 8, только в днях.

::: figure cohort-edge
Сверху — какие клетки таблицы удержания вообще можно заполнить: «есть» — месяц наблюдали, «пусто» — он ещё не наступил. Зелёным — клетки k = 1 и k = 2 когорт марта–июня, их сравнивает шаг 10. Снизу — шаг 8: у гостя с первым заказом 20 июня все 30 дней на возврат лежат внутри данных, а у гостя с первым заказом 20 августа видно только 12 дней. Поэтому в шаге 8 берут гостей с первым заказом до 1 августа.
:::

::: warn Типичные ошибки проекта
- **`COUNT(*)` после соединения с позициями.** `orders JOIN items` — это строки позиций: 22 813, а не 14 510. Заказы считают `COUNT(DISTINCT order_id)`.
- **Выручка как `SUM(price)`.** Забыто количество: позиция «2 капучино» стоит `qty * price`. На этих данных ошибка занижает выручку на 11 % — и ничем не выдаёт себя.
- **Средний чек как `AVG(qty * price)` по позициям.** Это средняя стоимость позиции, а не заказа. Сначала сумма по заказу (CTE), потом среднее.
- **`LEFT JOIN` превратился во внутренний.** Условие на правую таблицу в `WHERE` (`WHERE o.channel = 'зал'`) выбрасывает строки, где справа `NULL`, — гости без заказов пропадут. Такие условия ставят в `ON`.
- **Когорта по дате регистрации.** Гость из приложения мог зарегистрироваться в марте, а прийти в апреле или вообще не прийти. Когорта удержания — по первому **заказу**; регистрации без заказов — отдельная метрика (шаг 4).
- **Неполные месяцы когорт сравнивают с полными.** Удержание месяца 2 у июльской когорты не наблюдалось — его нельзя считать нулём или усреднять с остальными.
- **«Акция подняла продажи в два раза».** В июле вырос спрос на лимонад — но июль ещё и разгар лета. Без контрольной группы это совпадение, а не измеренный эффект.
:::

```python
import pandas as pd
import matplotlib.pyplot as plt                # библиотека графиков; pandas рисует через неё

t = pd.DataFrame({"month": ["2026-03", "2026-04", "2026-05", "2026-06"],

ax.set_xlabel("месяц")
ax.set_ylabel("тыс. ₽")
ax.axvspan(1, 2, alpha=0.2)                    # полоса от 2-й до 3-й точки: месяцы акции
plt.show()
```

Что здесь происходит:

- `plt.show()` показывает график. Столбчатая диаграмма — то же самое с `t.plot(kind="bar")`.

```python
import duckdb
import pandas as pd

names = ["shops", "menu", "guests", "promos", "orders", "items"]
dates = {"orders": ["ordered_at"], "guests": ["reg_date"], "promos": ["start_date", "end_date"]}
for name in names:
    t = pd.read_csv(f"zdb_{name}.csv", parse_dates=dates.get(name, []))
    duckdb.sql(f"CREATE OR REPLACE TABLE {name} AS SELECT * FROM t")

sizes = {name: duckdb.sql(f"SELECT COUNT(*) FROM {name}").fetchone()[0] for name in names}
empty_orders = duckdb.sql("""
    SELECT COUNT(*) FROM orders AS o
    WHERE NOT EXISTS (SELECT 1 FROM items AS i WHERE i.order_id = o.order_id)
""").fetchone()[0]
print(sizes, empty_orders)
```

### explain
В базе 14 510 заказов и 22 813 позиций — в среднем 1.6 позиции на заказ. Пустых заказов нет: каждый «шапочный» заказ имеет хотя бы одну позицию. Проверять это стоит всегда: заказ без позиций выпадет из внутреннего `JOIN orders ... items` и молча исчезнет из числа заказов. `NOT EXISTS` — самый надёжный способ найти «чего нет»: в отличие от `NOT IN`, он не ломается, если в подзапросе встретится `NULL`.
