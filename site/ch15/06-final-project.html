Финальный проект курса

Финальная работа курса и последний шаг основного пути (после итогового проекта главы 8) — от сырой базы до упакованной модели и рекомендаций в рублях. Направление «Зерно для офиса» теряет корпоративных клиентов и хочет каждый квартал получать список офисов, которым стоит позвонить. Собираете признаки из пяти таблиц CRM по срезам во времени, сравниваете три класса моделей, переводите прогноз в деньги, выпускаете модель как артефакт со скриптом расчёта и оформляете всё блокнотом и репозиторием для портфолио.

Бриф

Коллеги, у нас есть время не более чем на 150 звонков удержания за квартал. Для сравнения берите действующие офисы по возрастанию revenue_trend — нормированного изменения нетто-выручки за два соседних окна по 90 дней. При равенстве раньше идёт меньший client_id. В CRM нет журнала назначений звонков, поэтому это воспроизводимый ориентир.

Нужен список на квартал: кому звонить и в каком порядке. При звонке менеджер предлагает скидку 10 % на 2 месяца. Для сценарного расчёта предполагаем, что звонок удерживает половину офисов, которые иначе ушли бы. В этой CRM назначение звонка и его контроль не наблюдались; причинный эффект 0.5 здесь не измерен. Час менеджера с подготовкой обходится нам в 1 500 ₽ на звонок. Маржа направления — 35 % от выручки, сохранённую маржу в сценарии считаем за 12 месяцев при постоянной месячной выручке.

Сравните стратегии при одной мощности и укажите расходы каждой. Что мы вправе рекомендовать сейчас, какие связи стоит исследовать и что потребуется измерить в пилоте? Следующий квартальный список должен уметь пересчитать другой аналитик.

Происхождение и границы данных. Это синтетическая CRM на 01.10.2026. У файла office.db этого выпуска SHA-256 ec4fae8730a68fb4f2508ece2003efc017f19ff5457c1c87eee12dcb083c019f. Генератор сначала моделирует состояние офиса по месяцам до расторжения или конца наблюдения. Затем при создании прошлых недельных заказов он использует последнее состояние health и уменьшает интенсивность перед уже выбранной датой ухода. Поэтому для одной прошлой недели возможны разные интенсивности при разных последующих состояниях. Отбор по дате, календарный тест и проверку доступности признаков можно выполнить на этой CRM. Величина и направление отличия результата от будущих реальных кварталов неизвестны. Для оценки влияния звонка понадобятся реальные назначения и контроль.

Порядок работы.

До разбора выберите собственное правило: каким офисам звонить при ёмкости не больше 150 и данной экономике. Допустимы простой вероятностный классификатор, обоснованный короткий список и отказ при неположительной ожидаемой пользе. В паспорте запишите call_limit, если используете меньшую ёмкость, а в отчёте объясните её. Оглавление блокнота/README должно вести к списку, денежным допущениям и команде запуска.

  1. Скопируйте шаблон project-template.ipynb в site/notebooks/final_project.ipynb — тогда путь DATA = Path('../data') из первой ячейки подойдёт, база лежит в DATA / 'office.db'.
  2. Пройдите шаги ниже. Каждый шаг — раздел блокнота с кодом и markdown-выводом «что увидели и что это значит для бизнеса». Числа для самопроверки — в описании шагов и в задачах в браузере.
  3. Вынесите функции признаков в src/features.py, напишите score.py, сохраните артефакт.
  4. Скачайте check_notebook.py и requirements.txt. В папке блокнота выполните uv run --with-requirements requirements.txt python check_notebook.py final_project.ipynb --timeout 1800. Обязательны запуск с чистого ядра, отсутствие пунктов «Надо исправить» и проверка расчётов по рубрике. Дополнительный режим --project ch15/06-final-project рассчитан на имена переменных и сигнатуры семи браузерных карточек, требует dsc.py и папку tasks/ из комплекта курса (для другой папки укажите --course). В модульном проекте функция может принимать таблицы параметром и сохранять выводы в файлы. Тогда число совпавших интерфейсов, например 1/7, характеризует совместимость с карточками. Откройте блокнот и фактические файлы в чистой папке и проверьте расчёты по ключам, вероятностям, сумме и инструкции для получателя.
  5. Передайте коллеге блокнот, перечисленные файлы и чек-лист. Если доступен навык ds-project-review, его можно использовать для отдельного ревью. Укажите в README команды для запуска и проверки. В репозитории zerno-office/ положите базу в data/office.db и задайте DATA = Path("data") относительно корня. После замечаний повторите затронутые вычисления и передачу из чистой папки.

Постановка: срезы во времени

Зачем. Модель будет работать так: в последний день квартала берём всех действующих клиентов и по их истории оцениваем, кто расторгнет договор в следующие три месяца. Обучающие данные должны выглядеть точно так же — иначе модель учится не на той задаче.

Аналогия

Срез — как фотография офиса на дату: всё, что было до неё, на фото есть, всего, что случилось после, — нет. Цель — подпись под фотографией, которую мы узнаём через три месяца: «ушёл» или «остался». Для обучения нужны старые фотографии с уже известными подписями; для работы — свежая фотография, подпись к которой ещё предстоит угадать.

Игрушечный пример — один офис, договор с 10 марта 2025, расторгнут 14 февраля 2026:

срез действует на дату среза? ушёл в следующие 3 месяца? строка в данных
30.09.2025 да нет (до 31.12 договор действует) признаки на 30.09, цель 0
31.12.2025 да да (14.02 ≤ 31.03) признаки на 31.12, цель 1
31.03.2026 нет — уже ушёл — строки нет

Один клиент дал две строки обучения. Срезы проекта:

срез роль горизонт цели
30.09.2025, 31.12.2025, 31.03.2026 обучение и кросс-валидация следующие 3 месяца
30.06.2026 отложенная проверка (тест), открываем один раз июль–сентябрь 2026
30.09.2026 работа: список звонков на IV квартал неизвестна 
import sqlite3
import pandas as pd

con = sqlite3.connect("office.db")
base = pd.read_sql("""
    SELECT c.client_id, c.city, c.employees, k.plan, k.start_date, k.end_date
    FROM clients c JOIN contracts k USING (client_id)
    WHERE c.is_test = 0
""", con, parse_dates=["start_date", "end_date"])
con.close()

def build_target(cutoff, months=3):
    c = pd.Timestamp(cutoff)
    active = base[(base["start_date"] <= c) & (base["end_date"].isna() | (base["end_date"] > c))]
    if c + pd.offsets.MonthEnd(months) > pd.Timestamp("2026-09-30"):
        return pd.Series(pd.NA, index=active["client_id"].values, dtype="Int64", name="churn")
    left = active["end_date"].notna() & (active["end_date"] <= c + pd.offsets.MonthEnd(months))
    return pd.Series(left.astype(int).values, index=active["client_id"].values, name="churn")

for cut in ["2025-09-30", "2025-12-31", "2026-03-31"]:
    y = build_target(cut)
    print(cut, "действующих:", len(y), "ушли за 3 месяца:", int(y.sum()), "доля:", round(y.mean(), 3))

Что здесь происходит:

  • SQL-запрос соединяет клиентов с договорами и сразу отбрасывает тестовых — фильтр в базе дешевле, чем в pandas.
  • active — договор начался не позже среза и на дату среза не расторгнут (end_date пусто или позже среза).
  • left — договор расторгнут до конца третьего месяца после среза включительно. pd.offsets.MonthEnd(3) от 30.09 даёт 31.12, от 31.03 — 30.06: окно совпадает с кварталом. Простое pd.DateOffset(months=3) от 30.09 дало бы 30.12, и уход 31 декабря выпал бы из цели.
  • Результат — Series «клиент → 0/1» для действующих на срез клиентов.

Точные правила, по которым посчитаны контрольные числа (по ним же работает эталон в задачах ниже):

  • Окна. «За 90 дней» — даты в полуинтервале (срез − 90 дней; срез], то есть день среза входит. «Предыдущие 90» для revenue_trend — (срез − 180 дней; срез − 90 дней].
  • Заказы. Отменённые не считаем нигде; возвраты входят в число заказов и в выручку со знаком минус. revenue_trend = (выручка 90 − выручка предыдущих 90) / (выручка 90 + выручка предыдущих 90 + 1). При нулевом знаменателе соглашение этого выпуска — 0. При ненулевом сохраните результат полной формулы, включая значения за пределами [−1, 1].
  • days_since_order — дней от последнего неотменённого заказа (до среза включительно) до среза; если заказов не было — tenure_days.
  • late_share_90 — среди заказов за 90 дней со статусом «доставлен» доля с late_min > 0. Если доставленных заказов нет — 0.
  • Обращения — после drop_duplicates("ticket_id"), по created_at в окне 90 дней.
  • pay_late_last3. Берём счета с due_date не позже среза. Оплату после среза считаем неизвестной: paid_date → пусто. Просрочка счёта = (дата оплаты, а если её нет — дата среза) − due_date в днях, отрицательная → 0: оплата раньше срока — это 0 дней. «Три последних» — по due_date. Признак — среднее по ним; у клиента без счетов — 0.
  • overdue_now — счета с due_date раньше даты среза, не оплаченные на дату среза.

Здесь 0.5 — доля удержанных среди собиравшихся уйти, 0.35 · 12 · R — маржа за год, 1 500 ₽ — час менеджера, 0.2 · R — скидка 10 % на 2 месяца, которую получает каждый, кому позвонили. Звоним тем, у кого ожидаемая прибыль положительна, по убыванию, не больше 150.

Справка: пакетный скрипт `score.py`

Скрипт — это тот же код, что в блокноте, но запускаемый из терминала одной командой и с параметром. Договоритесь о схеме функции в src/features.py. Вариант интерфейса — build_features(tables, cutoff) принимает пять таблиц под именами из словаря и дату, возвращает DataFrame с уникальным индексом client_id и упорядоченными признаками из паспорта. Одна и та же функция приводит даты, исключает тестовых клиентов, обрабатывает возвраты, дубли и окна и используется и в блокноте, и в CLI. build_target(tables, cutoff) возвращает Series по тем же ID; для незакрытого горизонта значения неизвестны.

Пример аргументов и выпуска списка (после импортов argparse, sqlite3, json, joblib, pandas as pd, Path и вашей build_features). Запускайте из корня репозитория. Перед расчётом коллега сверяет отпечаток БД и версии с паспортом.

parser = argparse.ArgumentParser()
parser.add_argument("--cutoff", required=True)
parser.add_argument("--db", default="data/office.db")
parser.add_argument("--call-limit", type=int)
parser.add_argument("--output", type=Path)
args = parser.parse_args()
folder = Path("models/office_churn/1.0")
card = json.loads((folder / "passport.json").read_text(encoding="utf-8"))
model = joblib.load(folder / "model.joblib")
limit = card.get("call_limit", 150) if args.call_limit is None else args.call_limit
if not 0 <= limit <= 150:
    parser.error("Лимит должен быть от 0 до 150")
with sqlite3.connect(args.db) as con:
    tables = {name: pd.read_sql(f"SELECT * FROM {name}", con)
              for name in ["clients", "contracts", "orders", "tickets", "invoices"]}
features = build_features(tables, pd.Timestamp(args.cutoff))
offices = features.reset_index()
pos = list(model.classes_).index(1)
offices["p_churn"] = model.predict_proba(features[card["features"]])[:, pos]
R = offices["revenue_90"] / 3
offices["exp_profit"] = offices["p_churn"] * .5 * .35 * 12 * R - 1500 - .2 * R
calls = offices.loc[offices.exp_profit > 0].sort_values(
    ["exp_profit", "client_id"], ascending=[False, True]).head(limit)
out = calls[["client_id", "city", "p_churn", "exp_profit"]].copy()
out = out.round({"p_churn": 3, "exp_profit": 0})
suffix = "" if args.call_limit is None else f"_k{limit}"
output = args.output or Path(f"reports/call_list_{args.cutoff}{suffix}.csv")
output.parent.mkdir(parents=True, exist_ok=True)
out.to_csv(output, index=False)
print(len(out), round(float(calls.exp_profit.sum())))

Оба запуска используют один артефакт и дату; временный лимит действует только на конкретную очередь. Паспорт хранит лимит, число и сумму исходного выпуска. Что запомнить

  • Задача на отток по данным CRM решается срезами: дата среза → признаки только из прошлого → цель из следующих 3 месяцев. Срезов для обучения несколько, проверка — на более позднем срезе.
  • Одна функция build_features(tables, cutoff) для обучения и для работы: так признаки при расчёте списка совпадают с признаками при обучении.
  • Утечки в многотабличных данных прячутся в датах: заказы, оплаты и обращения после среза. Подозрительно сильный признак (AUC 0.98) — повод искать утечку, а не радоваться.
  • Один клиент в нескольких срезах — группа: кросс-валидация GroupKFold по client_id, иначе модель «узнаёт» клиента.
  • Модели сравнивают на одних фолдах и выбирают по кросс-валидации; тест на позднем срезе открывают один раз.
  • Решение — по ожидаемой прибыли каждого звонка: p · (доля спасённых) · ценность клиента − стоимость контакта, с ограничением на число звонков. Вероятности должны быть откалиброваны, иначе ожидаемая оценка чувствительна к качеству вероятностей.
