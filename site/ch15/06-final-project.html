Финальный проект курса

Финальная работа курса и последний шаг основного пути (после итогового проекта главы 8) — от сырой базы до упакованной модели и рекомендаций в рублях. Направление «Зерно для офиса» теряет корпоративных клиентов и хочет каждый квартал получать список офисов, которым стоит позвонить. Собираете признаки из пяти таблиц CRM по срезам во времени, сравниваете три класса моделей, переводите прогноз в деньги, выпускаете модель как артефакт со скриптом расчёта и оформляете всё блокнотом и репозиторием для портфолио.

Данные урокаoffice.db5608 КБВ примерах файлы уже подключены — скачивать нужно, только чтобы открыть их у себя.
0 из 6

Бриф

Коллеги, направление «Зерно для офиса» растёт, но и уходят от нас всё чаще: во втором квартале 2026 года расторгли договор 13 % офисов, а в IV квартале 2025-го — 6.5 %. За офисами закреплены менеджеры по продажам, и у них есть время примерно на 150 звонков удержания в квартал. Сейчас звонят тем, кто сам пожаловался, — обычно уже поздно.

Нужен список на квартал: кому звонить и в каком порядке. При звонке менеджер предлагает скидку 10 % на 2 месяца. По опыту прошлых акций примерно половину офисов, собиравшихся уйти, такой звонок удерживает. Час менеджера с подготовкой обходится нам в 1 500 ₽ на звонок. Маржа направления — 35 % от выручки, удержанный офис в среднем остаётся с нами ещё год.

Хочу понимать: сколько мы на этом заработаем по сравнению с «позвонить всем» и с нашим правилом «звонить тем, у кого падают заказы»; почему офисы уходят и что из этого можно исправить без звонков. И чтобы список на следующий квартал аналитик B2B мог пересчитать сам, без вас.

Порядок работы.

  1. Скопируйте шаблон project-template.ipynb в site/notebooks/final_project.ipynb — тогда путь DATA = Path('../data') из первой ячейки подойдёт, база лежит в DATA / 'office.db'.
  2. Пройдите шаги ниже. Каждый шаг — раздел блокнота с кодом и markdown-выводом «что увидели и что это значит для бизнеса». Числа для самопроверки — в описании шагов и в задачах в браузере.
  3. Вынесите функции признаков в src/features.py, напишите score.py, сохраните артефакт.
  4. Самопроверка: python check_notebook.py final_project.ipynb --timeout 1800 (из папки site/notebooks) — без пунктов «Надо исправить». С переменными, названными как в задачах шагов, python check_notebook.py final_project.ipynb --timeout 1800 --project ch15/06-final-project сверит и числа с эталонами.
  5. Ревью навыком ds-project-review, одна итерация доработки по замечаниям, затем — репозиторий на GitHub. Навык (skill) — готовая инструкция для Claude: с ней Claude проверяет блокнот по списку из раздела «Чек-лист ревью» ниже и возвращает замечания по структуре, коду и результату, не решая проект за вас. Как запустить: в Claude, где этот навык подключён (Claude Code или приложение Claude), приложите final_project.ipynb и попросите «сделай ревью навыком ds-project-review». Ответ — список замечаний: что исправить обязательно и что желательно. Если навыка у вас нет, пройдите чек-лист сами или отдайте его вместе с блокнотом коллеге.

Справка: база из Python

Все шаги проекта читают данные из office.db одной и той же схемой из трёх действий: открыть подключение, прочитать запрос в DataFrame, закрыть подключение.

import sqlite3
import pandas as pd

con = sqlite3.connect("office.db")       # 1. подключение к файлу базы

orders = pd.read_sql("SELECT * FROM orders", con, parse_dates=["order_date"])   # 2. запрос → DataFrame

Что здесь происходит:

  • sqlite3.connect("office.db") открывает файл базы и возвращает подключение con — «линию», по которой идут запросы.
  • pd.read_sql(текст_запроса, con) отправляет SQL в базу и складывает ответ в DataFrame: столбцы — как в SELECT. sqlite_master — служебная таблица SQLite со списком таблиц базы.
  • parse_dates=["order_date"] — SQLite хранит даты строками ГГГГ-ММ-ДД; так pandas сразу превратит их в даты.
  • con.close() закрывает подключение. Прочитанные таблицы остаются в памяти, а новый запрос через закрытое con упадёт с Cannot operate on a closed database — откройте подключение заново.

Постановка: срезы во времени

Зачем. Модель будет работать так: в последний день квартала берём всех действующих клиентов и по их истории оцениваем, кто расторгнет договор в следующие три месяца. Обучающие данные должны выглядеть точно так же — иначе модель учится не на той задаче.

Аналогия

Срез — как фотография офиса на дату: всё, что было до неё, на фото есть, всего, что случилось после, — нет. Цель — подпись под фотографией, которую мы узнаём через три месяца: «ушёл» или «остался». Для обучения нужны старые фотографии с уже известными подписями; для работы — свежая фотография, подпись к которой ещё предстоит угадать.

Игрушечный пример — один офис, договор с 10 марта 2025, расторгнут 14 февраля 2026:

срез действует на дату среза? ушёл в следующие 3 месяца? строка в данных
30.09.2025 да нет (до 31.12 договор действует) признаки на 30.09, цель 0
31.12.2025 да да (14.02 ≤ 31.03) признаки на 31.12, цель 1
31.03.2026 нет — уже ушёл — строки нет

Один клиент дал две строки обучения. Срезы проекта:

срез роль горизонт цели
30.09.2025, 31.12.2025, 31.03.2026 обучение и кросс-валидация следующие 3 месяца
30.06.2026 отложенная проверка (тест), открываем один раз июль–сентябрь 2026
30.09.2026 работа: список звонков на IV квартал неизвестна 
import sqlite3
import pandas as pd

con = sqlite3.connect("office.db")
base = pd.read_sql("""
    SELECT c.client_id, c.city, c.employees, k.plan, k.start_date, k.end_date
    FROM clients c JOIN contracts k USING (client_id)
    WHERE c.is_test = 0
""", con, parse_dates=["start_date", "end_date"])
con.close()

def build_target(cutoff, months=3):
    c = pd.Timestamp(cutoff)
    active = base[(base["start_date"] <= c) & (base["end_date"].isna() | (base["end_date"] > c))]
    left = active["end_date"].notna() & (active["end_date"] <= c + pd.DateOffset(months=months))
    return pd.Series(left.astype(int).values, index=active["client_id"].values, name="churn")

for cut in ["2025-09-30", "2025-12-31", "2026-03-31", "2026-06-30"]:
    y = build_target(cut)
    print(cut, "действующих:", len(y), "ушли за 3 месяца:", int(y.sum()), "доля:", round(y.mean(), 3))

Что здесь происходит:

  • SQL-запрос соединяет клиентов с договорами и сразу отбрасывает тестовых — фильтр в базе дешевле, чем в pandas.
  • active — договор начался не позже среза и на дату среза не расторгнут (end_date пусто или позже среза).
  • left — договор расторгнут в окне «срез + 3 месяца» (pd.DateOffset(months=3) — календарные месяцы).
  • Результат — Series «клиент → 0/1» для действующих на срез клиентов.

Что получилось: действующих клиентов от среза к срезу больше (628 → 965), а доля ушедших выросла с 6.5 % до 13–14 % — бриф подтверждается. Тест (30.06.2026) заметно «тяжелее» обучения (9.3 % по трём срезам вместе): модель придётся проверять в изменившемся мире, и это честнее, чем проверять на перемешанных строках.

Типичные ошибки постановки
  • Один срез «на сегодня» и цель «ушёл когда-нибудь». Ушедшие давно и действующие сравниваются по разным периодам жизни, признаки «последних 90 дней» у ушедших — нули по определению. Модель выучит «нет заказов — ушёл», а это следствие ухода, а не предвестник.
  • Признаки по всей таблице без фильтра по дате. orders.groupby("client_id") без order_date <= cutoff тянет заказы из будущего — проверка в задаче «Утечка через дату».
  • Перемешанный KFold по строкам. Один клиент в трёх срезах — три похожие строки. Если они попадут в разные фолды, модель «узнает» клиента, и оценка исказится: в этом проекте у kNN она вырастет с 0.714 до 0.733. Нужен GroupKFold(groups=client_id).

Шаг 3. Признаки на срез (3. Предобработка). Функция build_features(cutoff) — по строке на действующего клиента, всё строго по данным до среза включительно:

группа признаки
профиль employees, has_manager, own_machine, plan, city, industry (пропуск → «нет данных»), tenure_days — дней с начала договора
заказы за 90 дней orders_90 — число (без отменённых), revenue_90 — выручка, revenue_trend — (выручка 90 дней − выручка предыдущих 90) / (их сумма + 1), от −1 до 1; days_since_order — дней с последнего заказа; late_share_90 — доля доставленных заказов с опозданием
обращения за 90 дней tickets_90, tickets_bill_90 (категория «счёт»), после удаления дублей
оплаты pay_late_last3 — средняя просрочка трёх последних счетов со сроком до среза (оплата после среза = не оплачен, просрочка до даты среза); overdue_now — просроченных неоплаченных счетов на дату среза

Точные правила, по которым посчитаны контрольные числа (по ним же работает эталон в задачах ниже):

  • Окна. «За 90 дней» — даты в полуинтервале (срез − 90 дней; срез], то есть день среза входит. «Предыдущие 90» для revenue_trend — (срез − 180 дней; срез − 90 дней].
  • Заказы. Отменённые не считаем нигде; возвраты входят в число заказов и в выручку со знаком минус. revenue_trend = (выручка 90 − выручка предыдущих 90) / (выручка 90 + выручка предыдущих 90 + 1).
  • days_since_order — дней от последнего неотменённого заказа (до среза включительно) до среза; если заказов не было — tenure_days.
  • late_share_90 — среди заказов за 90 дней со статусом «доставлен» доля с late_min > 0. Если доставленных заказов нет — 0.
  • Обращения — после drop_duplicates("ticket_id"), по created_at в окне 90 дней.
  • pay_late_last3. Берём счета с due_date не позже среза. Оплату после среза считаем неизвестной: paid_date → пусто. Просрочка счёта = (дата оплаты, а если её нет — дата среза) − due_date в днях, отрицательная → 0: оплата раньше срока — это 0 дней. «Три последних» — по due_date. Признак — среднее по ним; у клиента без счетов — 0.
  • overdue_now — счета с due_date раньше даты среза, не оплаченные на дату среза.

Самопроверка на срезе 30.06.2026: 965 строк, средние orders_90 ≈ 13.23, revenue_90 ≈ 39 916 ₽, late_share_90 ≈ 0.080, tickets_90 ≈ 0.623, pay_late_last3 ≈ 0.944. Обучающая таблица — три среза вместе: 2 279 строк, 985 разных клиентов, доля ушедших 0.093.

Шаг 6. Деньги (4. Анализ, 5. Выводы). Для клиента с выручкой за месяц R (это revenue_90 / 3) и вероятностью ухода p:

E[\text{прибыль звонка}] = p \cdot 0.5 \cdot 0.35 \cdot 12 \cdot R \;-\; 1500 \;-\; 0.2 \cdot R

Здесь 0.5 — доля удержанных среди собиравшихся уйти, 0.35 · 12 · R — маржа за год, 1 500 ₽ — час менеджера, 0.2 · R — скидка 10 % на 2 месяца, которую получает каждый, кому позвонили. Звоним тем, у кого ожидаемая прибыль положительна, по убыванию, не больше 150.

Список выбирают по ожидаемой прибыли с p модели, а оценивают по фактическим уходам теста: в ту же формулу вместо p подставляют настоящий churn (0 или 1). Самопроверка на тесте: логистическая регрессия выбирает 66 офисов, из них 34 действительно ушли бы, итог ≈ +260 тыс. ₽ за квартал; правило «150 офисов с самым сильным падением выручки» — ≈ −227 тыс. ₽; «позвонить всем» — ≈ −2.45 млн ₽. Покажите чувствительность к доле удержанных: при 0.3 — 34 звонка и ≈ +70 тыс. ₽, при 0.7 — 97 звонков и ≈ +501 тыс. ₽.

Ожидаемая картина: сильнее всего — меньше заказов за 90 дней, больше обращений, Уфа, а персональный менеджер и своя кофемашина удерживают. Осторожно с отраслями: их коэффициенты до ±0.45, но проверьте, улучшает ли отрасль кросс-валидацию, — возможно, это шум (у 1 000 клиентов на 8 отраслей мало данных). # дальше — ожидаемая прибыль звонка по формуле шага 6, отбор > 0, не больше 150

Модель выбрала для звонков 66 офисов, а у менеджеров есть время на 150. Что ответить руководителю, который просит «добить список до 150, раз время есть»?

  • [x] Остальные 84 звонка по нашей оценке убыточны: скидка и час менеджера стоят больше, чем ожидаемая польза; время менеджеров лучше потратить на продажи или на офисы Уфы, где проблема в доставке

    Ограничение «не больше 150» — потолок, а не план. Ожидаемая прибыль звонка ниже нуля — звонок в минус, даже если менеджер свободен.

  • [ ] Согласиться: чем больше звонков, тем больше спасённых офисов и прибыли

    Спасённых — больше, прибыли — меньше: каждый следующий звонок — офис с меньшей вероятностью ухода, а скидку получает каждый, кому позвонили.

  • [ ] Снизить порог вероятности до 0.5, чтобы попало больше офисов

    Порог по вероятности не учитывает выручку клиента: решение принимают по ожидаемой прибыли, а не по вероятности.

  • [ ] Пересобрать модель, чтобы она находила больше уходящих

    Модель тут ни при чём: число выгодных звонков задаёт экономика (стоимость звонка и скидки), а не качество ранжирования.

Шаг 6. Список звонков в рублях

Посложнее
↑ К теории: Шаги проекта

На тесте посчитаны вероятности ухода test["p"] (логистическая регрессия, обученная на train). Для каждого клиента: месячная выручка R = revenue_90 / 3, ожидаемая прибыль звонка exp = p · 0.5 · 0.35 · 12 · R − 1500 − 0.2 · R. Список звонков — клиенты с exp > 0 по убыванию exp, не больше 150. Посчитайте фактическую прибыль списка (в формуле вместо p — настоящий churn): profit_model (целые рубли), n_calls и caught — сколько из списка действительно ушли бы. Что запомнить

  • Задача на отток по данным CRM решается срезами: дата среза → признаки только из прошлого → цель из следующих 3 месяцев. Срезов для обучения несколько, проверка — на более позднем срезе.
  • Одна функция build_features(tables, cutoff) для обучения и для работы: так признаки при расчёте списка совпадают с признаками при обучении.
  • Утечки в многотабличных данных прячутся в датах: заказы, оплаты и обращения после среза. Подозрительно сильный признак (AUC 0.98) — повод искать утечку, а не радоваться.
  • Один клиент в нескольких срезах — группа: кросс-валидация GroupKFold по client_id, иначе модель «узнаёт» клиента.
  • Модели сравнивают на одних фолдах и выбирают по кросс-валидации; тест на позднем срезе открывают один раз.
  • Решение — по ожидаемой прибыли каждого звонка: p · (доля спасённых) · ценность клиента − стоимость контакта, с ограничением на число звонков. Вероятности должны быть откалиброваны, иначе ожидаемая прибыль врёт.
  • Сдача: блокнот по шаблону без ошибок с чистого ядра (check_notebook.py), артефакт модели с паспортом и контрольным набором, скрипт расчёта списка и README для портфолио.
